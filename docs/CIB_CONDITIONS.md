# 给定条件与状态锁定

普通检验继续使用 `engineVersion=cib-exact-1.0.0`，字段与原1.0.0输入兼容。状态锁定限制候选空间，但被锁因素仍须达到自己的最大支持分。

本轮增加专用计算版本 `cib-conditioned-1.0.0`。`prepareRun(project, options)` 可接收可选的 `conditionedStateIds: string[]`；非空时随RunInput冻结，不修改Project科学数据或原有锁定字段。旧版本输入不得携带非空给定条件，防止不识别条件的旧实现静默按普通方法解释。

给定状态限制候选空间，继续向其他因素提供影响，自身免于平衡判定。给定的含义是本次分析的计算前提，不代表政策不可控制、已经落实、有效或最优。这是项目的建模选择，不主张为新CIB理论。

## 评分范围

`buildMatrix(project, {year, selectedJudgmentIds, conditionedStateIds})` 在给定条件下只准备实际需要的评分：

- 不要求指向给定因素的评分；不填0替代。
- 给定来源只要求所选状态那一行。
- 其他接受判定的目标仍要求全部候选状态的评分；不能只填当前方案所选目标状态。
- `matrix.coverage` 描述这次条件计算的必需范围，不表示整个双向判断库已完整。

专用矩阵必须和RunInput中的给定状态、专用方法版本一起读取，不可脱离上下文当作完整普通CIB矩阵。普通模式下的完整性闸门不变。

## 验证与解释

给定状态须属于活动因素，每因素最多一个，至少保留一个接受判定的因素；与原锁定冲突时阻断。支持分轨迹只列接受判定的目标，不为免检因素伪造零分或裕度。指定配置不符合给定状态时返回 `consistent:false`、`violatesConditions`，不计算该配置的支持分。

同一因素既锁定又明确给定同一状态时，按给定条件免检；两者指定不同状态则阻断。仅仅锁定不能获得免检。

普通模式、给定条件与条件值切换均使旧会话结果过期。归档保留给定状态、冻结项目和实际矩阵，保存验证按相同条件从冻结项目重建输入。单格及批量敏感性只改本次必需评分。

## 界面与保存边界

检验页的“给定条件（可选）”逐因素选择给定状态，默认所有因素参与判定。条件在会话内保留，随检验JSON和命名检验记录归档；刷新后需重新设定，不能把历史条件自动当成当前选择。

给定条件下“检验我的方案”的即时结果只存会话，不覆盖原来的普通方案持久检验记录；需要保存时使用本次结果归档。场景报告、计算依据、计算过程页和归档比较均注明条件。

## 验收

`tests/conditioned-solver.test.mjs` 核对给定与锁定的不同结果、实际必需评分、非法条件、100张合成矩阵的独立加总、条件敏感性、报告、归档重放与防篡改。

`tests/conditioned-browser.cjs` 用手工构造的机制矩阵检查普通/给定切换、过期提示、反向评分缺失、原项目不变、真实JSON下载、移动宽度及年度方案与给定状态矛盾的提示。示例不提供河北实证结论。
